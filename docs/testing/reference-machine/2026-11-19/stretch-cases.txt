== The long crossing polygon: about a quarter of a second a cursor move

With the polygon, the candidate's preview costs 242-252 ms a cursor move on
both renderers, about four frames a second, against 4 ms without the
preview. polygon_probe.py, on the candidate, an 800 x 600 Top CadView over
the same 100000 lines, 3 warm-ups and 20 samples each:

  call                                                      median, ms
  doc.select_crossing_polygon(comb)  (one validation + a query)    4.122
  view.stretch_outlines, the polygon given once per entity (100)  248.741
  view.stretch_outlines, a rectangle per entity instead             0.114

The cause, in the code: the viewport passes the polygon once per selected
entity, and the bindings (`CadView.stretch_outlines` in
crates/arq-python/src/view.rs and `CadDocument.stretch_entities` in
crates/arq-python/src/documents.rs) validate each pair's polygon from
scratch with `SelectionPolygon::new`, whose self-intersection check
compares every edge with every other: 402 edges, about 80,000 edge
intersections, repeated 100 times on every cursor move. The commit pays
the same once (0.58 s in a profiled run made while a build was running). Validating each distinct polygon
once and sharing it among its entities would leave about 4 ms. Not changed
in this session.

== Bulged polylines on the CPU

The candidate's CPU cursor frame with 100 two-arc polylines stretched is
24 ms (95th percentile 27 ms), over one 60 Hz frame; 8.8 ms without the
preview. The overlay then holds 209 one-pixel strokes. On the GPU the
frame fits (9.3 ms). Where the 15 ms goes was not looked into in this
session.

== Zoom and pan during the prompt

With the drawing redrawn on every move, the preview adds about 3 ms on the

display's refresh).
