CPU viewport: hairlines painted straight into the pixels, 2026-11-23

LMDE 7, Linux 6.12.118, Intel Core i7-2600, Mesa 25.0.7, X11 (Cinnamon)
at 1920 x 1080 and 60 Hz. Base: main at cf0db83. Change: branch
feature/cpu-raster on top of it. Desktop idle: no browser, video or
streaming program open.

Cause
-----
The 2026-11-20 report (cpu-frame-timing.txt) put about two thirds of each
CPU frame inside tiny-skia. Reading tiny-skia 0.12 shows why: an
antialiased hairline is walked one pixel step at a time, and every step
hands a two-pixel mask to blit_mask, which runs the whole raster
pipeline (load the destination, source-over, lerp by the coverage,
store) for those two pixels. The per-call set-up costs far more than the
blend.

Change
------
crates/arq-render/src/hairline.rs ports tiny-skia's antialiased hairline
(scan/hairline_aa.rs, BSD-3-Clause) for the one case the viewport uses:
solid, opaque, butt-ended lines inside the canvas. The pipeline is
replaced by the blend it computes for an opaque color,
div255(d * (255 - c) + s * c), written straight into the pixmap's bytes.
Fills and dashed outlines still go through tiny-skia.

The pixels are the same, bit for bit:
- hairline_tests.rs: 8,000 random segments in 40 colors over dark, white
  and transparent backgrounds, and level, plumb, sub-pixel, crossing and
  over-511-pixel lines, compared with tiny-skia's stroke_path byte for
  byte. Removing one rounding term from the port makes both tests fail.
- raster_tests.rs: a drawing of lines, circles, arcs, a wide polyline's
  fill and dashed outlines, through two cameras on two backgrounds,
  compared with the former all-tiny-skia painter byte for byte.
  Drawing the dashed outlines solid makes it fail.
- The overlay captures of tools/gpu_viewport_check.py below are
  byte-identical between base and change (and not blank: 200 colors).

Criterion, cargo bench -p arq-render --bench raster, 100,000 entities at
1920 x 1080 (ms, median):

Case                       Base     Change   Ratio
render all (CPU)           100.08    44.83   0.448
render 1% (zoomed in)       14.75     7.04   0.477

The GPU cases of the same run moved 6-11% with no GPU code changed:
the noise of the session, not this change.

Real viewport: the CPU child of tools/gpu_viewport_check.py, 100,000
entities, 1200 x 650 viewport, 57 timed frames per operation. Base and
change alternated, three rounds, each with a fresh XDG_CONFIG_HOME,
LANG=C.UTF-8, QT_QPA_PLATFORM=xcb (ms, median / p95):

Round   Base pan     Change pan   Base zoom    Change zoom
1       46.1 / 51.6  18.6 / 21.3  60.4 / 67.7  29.3 / 32.3
2       45.2 / 52.0  18.4 / 23.1  58.7 / 65.2  28.5 / 33.1
3       44.6 / 51.8  18.5 / 22.3  59.9 / 65.7  29.0 / 32.5

Median of the three: pan 45.2 -> 18.5 ms (0.41), zoom 59.9 -> 29.0 ms
(0.48). A CPU pan frame now fits in about one refresh at 60 Hz and a
half; the 1080p GPU frame (one refresh, 16.6 ms) is still faster.

What is left in a CPU frame is mostly the trace: walking the scene,
flattening arcs and clipping (about 12 ms of a pan and 20 ms of a zoom
in the 2026-11-20 split), then the fills and the crop.
